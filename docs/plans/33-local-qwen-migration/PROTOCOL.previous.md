# Execution Protocol

This plan runs **unattended**. The guiding principle is **keep making progress**: resolve what
you can, amend what is wrong, defer what is heavy, and never halt over a single fixable issue.

Do not edit this file. Do not copy it into `index.md`.

## Per stage

1. **Pick the stage.** Read `state.json`. If a stage is `IN_PROGRESS`, a previous run died
   mid-stage — resume and finish it (inspect the working tree for partial work). Otherwise
   re-examine any `BLOCKED` stage whose `blocked_by` items are all resolved. Otherwise take the
   first `PENDING` stage whose `depends_on` are `DONE`.
2. **Read the stage brief.** Follow its links to `resources/` or `stages/NN-name/` only if it
   points there. Do not pre-read reference material you were not sent to.
3. **Orient.** Read the tail of `journal.md` for what the last run did. If the stage cites a
   decision, read that entry in `decisions.md`.
4. **Resolve ambiguity yourself.** There is no user to ask. Pick the interpretation that fits
   the codebase and existing conventions, record it in `decisions.md`, and proceed.
5. **Implement.** Use a dedicated GPT-5.6-Luna xhigh subagent for each focused investigation or
   light fix when the supervisor runtime provides one. Give it the full evidence and a narrow
   deliverable; do not delegate secrets.
6. **Validate.** Run the stage's verification and the test suite. GATE lines must pass; REPORT
   lines are measured and their values written to `journal.md`. If anything fails, triage below.
   **A green command is not evidence.** For every GATE value, name the input it was computed from
   and the defect that would turn it red. A verifying subagent audits that provenance; it is not
   handed the commands and expected outcomes.
7. **Record.** Append one entry to `journal.md`. Update `state.json` — it is the single status of
   record; `index.md` carries no status to update. Never silently drop a problem.
8. **Commit.** One atomic commit with the stage's message, including code, configuration, and plan
   files. A plan-only commit uses `docs(plan): ...`.

Repeat until every stage is `DONE`, `SKIPPED`, or terminally deferred, then sweep `backlog.md`.

## Triage — when something fails

**Light** — a failing test, lint error, missing import, or small compatibility bug. Delegate it to
one focused GPT-5.6-Luna xhigh subagent and retry at most twice. Re-run verification after each
attempt.

**Heavy** — architectural work, an external dependency, or an issue that survives two attempts.
Record a self-contained item in `backlog.md`, keep independent stages moving, and do not grind.

**Wrong gate** — the implementation is correct but a measurement threshold or precondition is
wrong. Amend only under the amendment rule below. **Unmeasurable** — the criterion is right but
this run cannot produce its evidence: record `NOT MEASURED` and let a GATE block; never substitute
a literal, default, midpoint, or fabricated row.

## Amendment rule

An amendment requires evidence in `journal.md`, a `decisions.md` entry quoting the original,
the original struck in place (`~~old~~ → new`), and the disposition in `state.json`. Measurement
thresholds, tolerance, sample counts, corpus assumptions, and false preconditions are amendable.
Tests, integrity, security, structural contracts, and explicit user directives are not.

## Disposition

- Core goal met, with any non-essential deferrals → `DONE`.
- A deferred item essential to that stage → `BLOCKED` with its backlog id.
- A conditional stage with no applicable work → `SKIPPED` and record why in `journal.md`.

**BLOCKED is not terminal and does not propagate.** A stage is blocked only by its own unmet gate.
If a dependency is blocked, a dependent stage remains `PENDING`; it is not marked blocked. When a
blocker resolves, re-examine the origin stage in the same commit.

## Guardrails

- Keep every commit buildable. Never weaken, skip, or delete a test to make it pass.
- Never generate an artefact to satisfy a declared count. A count floor is met only by real checks.
- A check that cannot fail is not a check. Every GATE status comes from this run's inputs and names
  the defect that would turn it red.
- Never print, log, or commit `VLLM_API_KEY` or any other secret. Read it from the environment only.
- Do not use `git commit --no-verify` or destructive repository commands.
- Do not certify on known-corrupt final evidence. If the harness or evidence is corrupt, make it a
  prerequisite stage with its own gate; do not defer it past the final decision.
